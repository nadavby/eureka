# Stage 5: Demo Mode Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task.

**Goal:** A recruiter clicks **Try the demo** and within seconds sees the whole product working: their own lost item, an AI match with a found item, a waiting chat message and a confirm flow that reaches the contact details. No sign-up, and no visitor ever sees or breaks another visitor's demo.

## Deviation from the spec (decided while planning)

The spec had **one shared demo user**. With several visitors, that account gets corrupted: one deletes an item, another confirms the match, and the next visitor lands in a broken state. Instead, every visitor gets a **private sandbox**.

## Rules

| Concept | Rule |
|---|---|
| `user.demoRole: "seed"` | Bots ("residents") that own the public demo items. Never log in. |
| `user.demoRole: "visitor"` | Created by `POST /auth/demo`. Can report items, chat and confirm. Cannot edit or delete the profile (`403 DEMO_READONLY`). Removed after 24 h. |
| `item.sandbox: true` | Every item owned by a visitor. Hidden from listings, the map and other people's public profiles, except for its owner. Never a *candidate* in vector search, but it can be a *query*, so a visitor's upload can still match seed items with real AI. |
| Confirming a match with a seed bot | The bot confirms right after the visitor does, so the flow completes. Only the visitor's item is resolved. Seed items stay open and keep their other matches, so every visitor sees the same world. |
| Chat with a seed bot | The bot answers the visitor's first message once, with a canned, item-specific reply. |
| Rate limits | `POST /auth/demo` is behind `authLimiter`. A global cap of 300 live visitors returns `503 DEMO_BUSY`. |

## Visitor starter scenario (created by `POST /auth/demo`)

1. Visitor user "Guest 4821".
2. The visitor's sandbox **lost** wallet: a copy of the seed template's fields and image URL, with no `imagePublicId`, so deleting it never deletes the shared image.
3. A **found** wallet owned by the bot "Noam", also sandboxed and owned for visibility by the visitor (`sandboxOwnerId`). Every visitor needs their own copy, so that confirming resolves it without touching others.
4. A match between the two, with a score of 92, the reasons and one conflict, plus 2 notifications.
5. A chat message from Noam: "Hi! I think I found your wallet near Habima Square. Can you tell me something that's inside, so I know it's yours?"

`item.sandboxOwnerId` (the visitor id) decides visibility. For the visitor's own items it equals `userId`. For bot copies made for a visitor, it's that visitor.

## Seed (`npm run seed:demo`)

- **Idempotent:** deletes all users with `demoRole`, plus their items, matches, chats, notifications and the demo images in storage. Then it recreates them.
- **4 bots:** Noam, Shira, Avi, Lena. About 10 open public items across categories (keys, phone, backpack, glasses, umbrella, headphones, watch, dog, bicycle, wallet), placed around Tel Aviv with place names. Each item is drawn as an SVG illustration, rasterized and stored through `processImage`/`imageStorage` in the `demo` folder.
- **Matching:** the seed runs `analyze-item` for each item through the queue (Gemini in production, or `AI_FAKE` locally), so the items have attributes and embeddings and visitor uploads can match them.
- **Nightly reset:** a GitHub Actions cron (`demo-reset.yml`, 03:00 UTC, plus manual dispatch) runs `npm run demo:cleanup` (visitors older than 24 h) and then `npm run seed:demo` against production secrets.

## Frontend

- **Try the demo** on the landing page and the login page, which calls `POST /auth/demo` and opens the visitor's match page.
- **Demo banner** in the shell for visitors: "You're in a demo. It resets every night." with a sign-out link.
- The profile page is read-only for visitors.
